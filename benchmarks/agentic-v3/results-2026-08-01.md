# Agentic benchmark v3 — results (2026-08-01)

18 graded runs: **6 real-world tasks × 3 builds × 1 fresh Haiku 4.5 agent each**, run
strictly sequentially against one live Opera instance. Method, tasks, and pinned answers:
[`suite.md`](suite.md). Raw per-call logs: [`logs/`](logs/). Harness: [`harness/`](harness/).

Two independent instruments, neither self-reported by the agent:

- **CLI shim** — every invocation logged with argv, exit code, wall time, and full output.
- **Subagent transcripts** — exact API usage per agent, costed at Haiku 4.5 rates
  ($1.00/M in, $5.00/M out, $1.25/M cache write, $0.10/M cache read).

**v3 is 58% cheaper than v1** on identical work — half the appended tokens, a third of the

Accuracy: **18/18 substantively correct**, all conditions. The only wobble is a shared
one — see C-1.

## Findings

### A-1 — Given `eval`, a small model never looks at a snapshot at all

The first two pilot runs (discarded, `logs/discarded-v*-t1.tsv`) were both solved with
`eval` + `document.querySelectorAll`/XPath — zero snapshots taken, v1 and v2
indistinguishable, ~26k tokens each. That is **cheaper than every graded run of the same
task** (v3's best was 33k). Haiku reaches for the DOM the moment it is offered.

The graded suite therefore forbids `eval`, but the implication for the product stands:
for read-only extraction, the whole compaction pipeline is bypassed by the cheapest path
the CLI itself advertises — `eval` appears in the contextual `help[]` block on *every*
snapshot. If snapshot quality is the product, `eval`'s prominence is working against it;
if `eval` is genuinely the better tool for extraction, that deserves to be a documented
strategy rather than an accident.

### A-2 — `find` and `chain` were used **zero times in 18 runs**, because `--help` doesn't list them

The command registry has 45 commands. The `--help` text is a hand-written string that
still says `commands[41]` and omits exactly the two new ones (`find`, `chain`); `flags[2]`
likewise lists only `--help` and `--version`, never `--full`, `--raw`, `--next`,
`--quiet`, or `--expect`. Every agent ran `help` and `--help` as instructed, and not one
discovered either command. `find` surfaces only in the post-truncation hint; `chain`,
`--quiet`, `--expect`, and `snapshot @ref` surface nowhere an agent will look.

Two of the branch's headline features are, in practice, dead code for an agent that
learns the tool from its own help. This is the cheapest fix in the whole review and
probably the largest remaining win — the measured v2→v3 delta (−10%) is what the branch
achieves *without* anyone using its new commands.

### A-3 — v3's strengthened truncation hint steered the agent to `--full`, not `--next`

The hint text differs exactly as designed:

- v2: ``Run `snapshot --next` to continue reading, or add `--full` for the complete snapshot``
- v3: ``Run `snapshot --next` to continue reading, `find "text"` to search, or add `--full` for everything``

On T1 the v2 agent used `--next` three times and emitted 76KB. The v3 agent used
`--full` four times and emitted 2.31MB — 30× more, and more than v1. Adding `find` to the
hint made the sentence a three-way choice whose last-named option is the expensive one.
n=1, so this is a hypothesis, not a measurement; but it is the opposite of the effect
claimed in `results-2026-07-18-v3.md`, and it is worth a deliberate wording test
(lead with `find`, describe `--full` as a last resort or drop it from the hint).

**Important caveat on why v3 still won T1 on cost:** Claude Code truncates oversized tool
output before it reaches the model, so those four `--full` calls cost the agent far less
context than they cost the CLI to emit. The `Bytes` and `Appended tokens` columns
disagree for exactly this reason. In a client without that cap, v3's T1 would have been
the most expensive run in the matrix, not the cheapest. **Bytes emitted is the metric
that generalises; appended tokens is the metric for this harness.**

### A-4 — v1's failure mode is `scroll` + `--full`, and it is brutal

Across the matrix v1 used `scroll down` 7× and `snapshot --full` 5×, emitting 3.1MB.
On T1 alone it took 131 agent turns and $0.58 — 3.6× v3 — because with no windowing and
no search it can only re-dump the whole document and scroll. This is the strongest
vindication of the branch: **windowing (`--next`) is what makes large documents tractable
at all**, and v2 already captured it.

### A-5 — Post-action diffs work, and cost almost nothing to have

On T2 (TodoMVC) v2 and v3 emitted 10.1KB against v1's 18.1KB for the same nine
interactions, with 37/40 turns against v1's 44. The diff path behaved as specified;
no condition failed the task. The effect is real but modest here — this page is small, so
even a full snapshot is cheap. Diffs should pay off much more on a large page with a
small mutation, which this suite does not yet contain (see "Suite gaps").

## Suite gaps (what a v4 should add)

1. **A large page with a small mutation** — the scenario post-action diffs are built for
   (e.g. a filter checkbox on a long search-results page). T2 is a small page; T1/T4/T5 are
   read-only. Nothing in this suite plays to D3's strength.
2. **A forced stale-ref recovery** — navigate away, come back, act on a pre-navigation ref.
   D2b (`nearestRefSuggestion`) was never triggered in 18 runs.
3. **A second consumer of the same page** — a task where one agent snapshots and another
   reads, which is where D7's "unchanged" short-circuit misfires (finding D-1 in the review).
4. **n ≥ 3 repeats.** Everything here is n=1 per cell. The v1→v3 gap (58%) is far larger
   than plausible per-cell noise, and it reproduces in the same direction on all three
   large-page tasks, so the headline is safe. The v2→v3 split (10%) is **not** resolvable
   at this sample size — treat it as "no regression", not as a measured win.
5. **A no-`eval` and a with-`eval` arm**, scored separately, so A-1 becomes a number
   rather than an anecdote.

## Reproducing

```sh
# build the three conditions (worktrees for v1/v2, HEAD in place)
git worktree add /tmp/wt-v1 main && git worktree add /tmp/wt-v2 d9a1f4f
(cd /tmp/wt-v1 && ln -s $PWD/node_modules . && npx tsc)   # same for wt-v2
npx tsc

harness/runctl.zsh switch v2          # kill + start that build's bridge, clear state
harness/gen.zsh v2 t4                 # → a logging wrapper for this (cond, task) cell
# hand the wrapper path to a fresh Haiku agent with the prompt from suite.md
harness/runctl.zsh reset v2           # between cells of the same condition
python3 harness/analyze.py            # both instruments → the tables above
```

`analyze.py` maps each cell to its subagent transcript by agent id; update the `RUNS`
table there when re-running.
